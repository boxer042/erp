## 1. 도메인 결정 사항 (재논의 필요 없음)

이 세션에서 사용자와 합의된 **도메인 정책 핵심 5가지**:

### 1.1 분할 발송 — 광의 정의

`Order.shipmentCount ≥ 2` 가 "분할" 로 표시되며, 두 케이스 모두 포함:

| 케이스 | 설명 |
|---|---|
| 수량 분할 | 한 OrderItem 의 10개 중 8개 + 2개 따로 발송 |
| 라인 분할 | 카트의 A품목 / B품목 을 별도 회차로 발송 (각 라인은 한 번에 다 보냈더라도) |

이유: 손님·매장 모두에게 "여러 박스 따로 도착" 사실 자체가 운영상 의미 있어서 광의 정의 채택. 단일 회차(=1)는 일반 발송으로 간주, 표시 안 함.

### 1.2 워크보드 행 모델 — 품목별 행 (네이버 스타일, B 안)

- 1 row = 1 OrderItem (이전엔 1 row = 1 Order)
- 같은 주문은 그룹화 — 첫 행에만 주문번호·고객·채널·결제·액션 노출
- 자식 행은 들여쓰기 + 자식 행 td-border-t-0 으로 같은 그룹임 시각 표시
- KPI 카운트는 **여전히 주문 단위** (행 늘어났다고 부풀지 않음 — `Set<orderId>.size`)
- 라인 진행률 progress bar 는 **라인 단위** (item.shippedQty / item.quantity)
- 분할 N회 칩은 order-level 정보이므로 그룹 첫 행에만

### 1.3 변형상품(variant) 과 고객 옵션(option) 분리

| | 변형상품 (variant) | 고객 옵션 (ProductOption) |
|---|---|---|
| **결정 주체** | 매장 (출고 시점) | 고객 (카탈로그·POS) |
| **노출** | canonical 만, variant 숨김 | 옵션 슬롯·값 노출 |
| **실현** | SetComponent + Assembly (조립 부속) | 옵션값마다 다른 처리 (3가지 모드) |
| **데이터 모델** | Product.canonicalProductId + variants (기존) | ProductOption + ProductOptionValue (신규) |

기존 변형상품 정의·인프라(Assembly·SetComponent·Inventory)는 **그대로 보존**. 옵션은 **별도 도메인**으로 추가.

### 1.4 옵션값 처리 3가지 모드

| 모드 | ProductOptionValue 필드 | OrderItem 처리 |
|---|---|---|
| (A) 단순 텍스트 | `mappedProductId=null, mappedVariantId=null` | MAIN 라인의 optionSnapshot 에 라벨 보존 (variant 자동 생성은 Phase 3) |
| (B) 매장 variant 매핑 | `mappedVariantId` | 결제 시 자동 Assembly 흐름 (Phase 3) |
| (C) 다른 Product 매핑 | `mappedProductId` | OPTION_REF 별도 OrderItem 라인 자동 생성 (parentItemId=메인) |

모드 C 는 메모리·SSD 같이 단독 판매도 되는 부속에 자연스러움. 단독 판매 + 옵션 판매가 같은 inventory source 공유.

### 1.5 시각 D 안 (옵션 표시)

- 메인: 표시 없음
- 옵션값(MAIN 라인): 상품명에 부속 텍스트 `(화이트 · L)`
- OPTION_REF 라인: outline info `[옵션]` 배지
- ADDON 라인: outline accent `[추가구매]` 배지 (후속 도메인)

## 2. 이번 세션에 만든 것

### 2.1 스키마 변경 ([prisma/schema.prisma](../prisma/schema.prisma))

```prisma
// 분할 송장
model Shipment        — orderId, shipmentNo (주문 안 unique), trackingCarrier, trackingNumber, shippedAt, memo
model ShipmentItem    — shipmentId, orderItemId, quantity

// 고객 옵션
model ProductOption       — productId, name, required, sortOrder, isActive
model ProductOptionValue  — optionId, label, addPrice, mappedProductId, mappedVariantId, sortOrder, isActive

// 기존 모델 확장
Order.shipmentCount       — Int default 0 (분할 발송 회차 카운트)
OrderItem.lineRole        — enum MAIN/OPTION_REF/ADDON
OrderItem.parentItemId    — self-relation (메인-옵션 트리)
OrderItem.optionSnapshot  — JSON (주문 시점 옵션값 보존)
```

dev DB 푸시 + Prisma client 재생성 완료. `Order.trackingCarrier/trackingNumber` 는 deprecated 캐시로 보존 (마지막 회차 송장 동기화).

### 2.2 신규 API

| 엔드포인트 | 역할 |
|---|---|
| `GET /api/orders` | items 에 lineRole/parentItemId/optionSnapshot 노출 + 검색에 상품명 포함 + partialState aggregate |
| `GET /api/orders/[id]` | shipments 회차순 + ShipmentItem 포함 |
| `PATCH /api/orders/[id]/shipments/[shipmentNo]` | 회차 송장 수정 |
| `DELETE /api/orders/[id]/shipments/[shipmentNo]` | 회차 취소 (shippedQty 복원 + 잔량 발생 시 status 복귀) |
| `GET/POST /api/products/[id]/options` | 옵션 목록 / 신규 |
| `PATCH/DELETE /api/products/[id]/options/[optionId]` | 옵션 upsert / soft delete |
| `POST /api/orders` | optionValueIds 처리 → optionSnapshot 자동 생성 + OPTION_REF 자식 라인 자동 생성 (모드 C) |

### 2.3 백엔드 흐름 변경

- `partial_ship` / `ship` 액션 — Shipment + ShipmentItem 자동 생성 + Order.shipmentCount 증가
- `Order create` — `items[].optionValueIds` 받아 처리:
  - 옵션값 일괄 조회 → addPrice 합산해 메인 unitPrice 에 반영
  - mappedProductId 있는 옵션값은 **OPTION_REF 자식 OrderItem 자동 생성** (수량은 메인과 동일)
  - parentItemId 매핑 위해 `prisma.$transaction` + 순차 생성

### 2.4 프론트엔드

| 영역 | 변경 |
|---|---|
| `/orders` 워크보드 | 품목별 행으로 마이그레이션. ItemPhaseBadge / ShipmentSummaryChip / PartialProgress 신규 컴포넌트 |
| `/orders` 상세 시트 | ShipmentHistoryCard 신규 (회차별 송장 + [수정]/[취소] 액션). itemId 하이라이트 + scrollIntoView |

### 3.3 추가상품 (ADDON) 도메인

- 추가상품 카탈로그: `BundleProduct` 모델 (메인 → 추천 추가상품 list)
- 메인 상품 페이지에서 추가상품 추천 노출
- 카트 담기 시 자동 ADDON 라인 생성
- 반품 cascade 정책 (메인 반품 시 ADDON 자동 같이? — 현재 합의: 일반적으로 cascade)

### 3.4 시각 / 운영 보강

- 부분 발송 dialog 가 회차별로 다른 송장 자동 노출 (이미 안내 박스 추가됨, dialog UI 그대로)
